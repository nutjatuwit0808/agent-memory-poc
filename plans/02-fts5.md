# Workshop 02 — SQLite FTS5

## คำถามตั้งต้น

- index เร็วกว่าเพราะอะไร (กลไกจริง ไม่ใช่ "เพราะมัน index ไว้")
- ต้องจ่ายอะไรแลก — เวลา build, พื้นที่, ความซับซ้อน
- "index stale" คือปัญหาอะไร เกิดตอนไหน แก้ยังไง

## ทฤษฎีสั้น (เขียนลง README ตอนทำ)

Inverted index = พลิกจาก "ไฟล์ไหนมีคำอะไร" เป็น "คำนี้อยู่ไฟล์ไหนบ้าง" → query เปลี่ยนจากสแกน corpus เป็น lookup + intersect posting list
BM25 เพิ่มสองอย่างที่ ripgrep ไม่มี: **IDF** (คำที่หายากมีน้ำหนักมากกว่า) และ **length normalization** (แก้ length bias ที่เจอใน WS01)
ราคาที่จ่าย: index ต้องถูก build ก่อน และมันไม่รู้ตัวเมื่อ vault เปลี่ยน

## W2-2 — Schema

**ไฟล์:** `src/search/backends/schema.sql` (แยกไฟล์ ให้อ่าน SQL ได้โดยไม่ต้องอ่าน TS)

**ทำ:**
- ตาราง `notes` เก็บ metadata: id, layer, created_at, content, content_hash, mtime
- ตาราง `note_tags` (id, tag) — normalize เพื่อให้ filter tag ทำใน SQL ได้
- virtual table `notes_fts` แบบ **external content** (`content='notes'`) + trigger sync

**ทำไม external content:** ไม่เก็บ text ซ้ำสองที่ → เห็นความต่างของ index size ชัด และการต้องเขียน trigger เองทำให้เห็นว่า "index ต้องถูก sync" เป็นงานที่มีอยู่จริง ไม่ใช่เวทมนตร์

**Tokenizer:** ระบุให้ชัดว่าเลือกอะไรและกระทบภาษาไทยยังไง — `unicode61` ตัดคำไทยไม่ได้ (ไทยไม่มีเว้นวรรค) ถ้า vault มีเนื้อหาไทยต้องจดข้อจำกัดนี้ลง README ว่าเป็นจุดที่ vector จะได้เปรียบใน WS03

**DoD**
- [ ] DDL อยู่ในไฟล์ `.sql` แยก มี comment ทุกตาราง
- [ ] มี trigger insert/update/delete ครบ
- [ ] จดพฤติกรรม tokenizer กับข้อความไทยลง README พร้อมตัวอย่างจริง
- [ ] ไม่มี ORM (CLAUDE.md §6)

## W2-3 — reindex.ts

**ไฟล์:** `src/cli/reindex.ts`

**ทำ:** vault-reader → เขียนลง SQLite ใน transaction เดียว → วัด buildTimeMs

**Incremental:** เทียบ `content_hash` ต่อ note แล้วอัปเดตเฉพาะตัวที่เปลี่ยน มี flag `--full` สำหรับ rebuild ทั้งหมด
ต้องวัดทั้งสองโหมดแล้วเทียบตัวเลข — full rebuild vs incremental (แก้ 1 ไฟล์) คือหลักฐานว่าทำไม production ต้องทำ incremental

- [ ] พิมพ์ buildTimeMs + ขนาดไฟล์ + จำนวน note ที่แตะจริง

## W2-4 — fts5.backend.ts

**ไฟล์:** `src/search/backends/fts5.backend.ts`

**ทำ:**
- `index()` → เรียก logic เดียวกับ reindex
- `search()` → `MATCH` + `bm25()` + filter layer/tag ใน `WHERE` ก่อน rank (**pre-filter** — ต่างจาก WS01)
- `stats()` → นับแถวจริง + `page_count * page_size` เป็น sizeBytes

**bm25() คืนค่าติดลบ (ยิ่งน้อยยิ่งดี)** ต้องแปลงเป็น score ที่มากคือดี ให้ตรงกับ interface — เขียน comment อธิบายไว้ ไม่งั้นคนอ่านสับสนแน่

**Escape:** ผู้ใช้พิมพ์ `"` หรือ `*` หรือ `OR` จะกลายเป็น FTS5 query syntax — ต้อง escape ด้วยการครอบ double quote และ escape `"` ข้างใน

**DoD**
- [ ] implement 3 method ครบ ไม่แก้ signature interface
- [ ] `matchedBy: "fts"`
- [ ] query ที่มี `"` `*` `OR` `NEAR` ไม่พัง
- [ ] SQL อยู่ในโค้ดแบบอ่านได้ ไม่ต่อ string แบบ inject ได้ (ใช้ bound parameter)
- [ ] filter ทำใน SQL จริง — พิสูจน์ด้วย `EXPLAIN QUERY PLAN` แปะลง README

## W2-5 — Stale index demo

**ทำ:** สาธิตให้เห็นกับตา — นี่คือ deliverable หลักของ workshop นี้ ไม่ใช่ของแถม

สคริปต์/ขั้นตอน: แก้ note ใน vault → search ทันที (ยังไม่ reindex) → ได้ผลเก่า → reindex → ได้ผลใหม่
เพิ่มการตรวจจับ: เทียบ mtime ของไฟล์กับที่เก็บใน DB แล้วเตือน `⚠ index stale: N notes changed`

**จดลง README:** ripgrep ไม่มีปัญหานี้เลยเพราะอ่านของจริงทุกครั้ง — นี่คือราคาที่แท้จริงของ index ไม่ใช่แค่ disk space

**DoD**
- [ ] ทำซ้ำได้ตามขั้นตอนที่เขียน มี output จริงแปะใน README
- [ ] มี stale detection ที่เตือนตอน search
- [ ] เขียนไว้ชัดว่า production แก้ปัญหานี้ยังไงบ้าง (file watcher / write-through / TTL) และ workshop นี้เลือกทางไหนเพราะอะไร
