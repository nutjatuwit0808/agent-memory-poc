# Workshop 07 — Cross-encoder reranking (2-stage retrieval)

## คำถามตั้งต้น

- cross-encoder ต่างจาก bi-encoder (WS03) ยังไง **ในทางกลไก** ไม่ใช่แค่ "แม่นกว่า"
- reranking ช่วยได้จริงแค่ไหน **เมื่อ precision@5 อยู่ที่ 89% ของเพดานอยู่แล้ว**
- แลกมากับ latency เท่าไหร่ และ candidate ควรเอามากี่ตัว

## ทฤษฎีสั้น (เขียนลง README ตอนทำ)

**bi-encoder (ที่ WS03 ใช้):** encode query กับ document **แยกกัน** แล้ววัด cosine — document embed ล่วงหน้าได้ ตอน query จึงเหลือแค่ lookup แต่ข้อเสียคือโมเดล**ไม่เคยเห็น query กับ document พร้อมกันเลย** ความสัมพันธ์ระหว่างสองฝั่งถูกบีบให้เหลือแค่มุมระหว่างเวกเตอร์

**cross-encoder:** ยัด `[query, document]` เข้าโมเดลพร้อมกันเป็นคู่ → attention มองข้ามไปมาระหว่างคำใน query กับคำใน doc ได้เต็มที่ → แม่นกว่ามาก แต่**คำนวณล่วงหน้าไม่ได้เลย** ต้อง forward pass ใหม่ทุกคู่ตอน query ต้นทุนจึงเป็น O(N) ต่อ query ไม่ใช่ O(1)

**2-stage:** ใช้ backend เดิมคัด candidate กว้างๆ (recall สำคัญกว่าลำดับ) → ส่งแค่ top-N ให้ cross-encoder จัดอันดับใหม่ (precision) — ตัวเลขที่วงการรายงาน: +17–66ms ต่อ query แลกกับ NDCG@10 ขึ้น 5–15 จุด

---

## ⚠️ ความเสี่ยงหลัก 2 ข้อ — ต้องเคลียร์ก่อนเขียนโค้ด

### 1. อาจไม่มี headroom ให้วัดเลยบน query set ปัจจุบัน

คำนวณจาก `bench/queries.json` แล้ว: 20 query มี relevant เฉลี่ย **1.85 ไฟล์** → **เพดานทฤษฎีของ precision@5 = 0.37** ซึ่ง `router-fuse` ทำได้ 0.33 แล้ว = **89% ของเพดาน** และ MRR 0.93 ก็เกือบชน

แปลว่า **reranking แทบไม่มีที่ให้ปรับปรุงบนชุดข้อมูลนี้** ถ้าลุยเขียนเลยแล้วได้ +0.01 จะสรุปผิดว่า "reranking ไม่มีประโยชน์" ทั้งที่จริงคือ**วัดด้วยไม้บรรทัดที่สั้นเกินไป**

### 2. โมเดล cross-encoder ยอดนิยมเป็น English-only

`ms-marco-MiniLM` (ตัวที่คนใช้กันมากสุด) เทรนบน MS MARCO ภาษาอังกฤษล้วน แต่ vault นี้เป็นไทยเป็นหลัก — ถ้าใช้ตัวนี้ตรงๆ อาจแย่ลงกว่าเดิมด้วยซ้ำ ต้องหา multilingual cross-encoder ให้ได้ก่อน (เช่นตระกูล `bge-reranker-v2-m3`) และ**ต้องเช็คว่ามี ONNX build ที่ transformers.js รันได้จริง**

## W7-1 — พิสูจน์ headroom ก่อน (ห้ามข้าม)

**ทำ:** ตอบให้ได้ด้วยตัวเลขว่า "ยังมีที่ให้ rerank ปรับปรุงไหม" ก่อนเขียน backend

1. คำนวณ **oracle ceiling** — ถ้าจัดอันดับได้สมบูรณ์แบบจาก candidate ที่ backend เดิมคัดมา (top-10) recall@5/MRR จะได้เท่าไหร่
2. เทียบกับที่ทำได้จริงตอนนี้ → **ช่องว่างตรงนี้คือทั้งหมดที่ reranking มีสิทธิ์ได้**
3. ถ้าช่องว่างเล็กเกินไป (< 0.05) → **ขยาย query set ก่อน** ให้มี query ที่มี relevant ≥3 ไฟล์ เพิ่มอีกอย่างน้อย 8 ข้อ

**DoD**
- [ ] มีตัวเลข oracle ceiling ของทุก backend บันทึกไว้
- [ ] ตัดสินด้วยตัวเลขว่าต้องขยาย query set หรือไม่ — ถ้าต้อง ทำให้เสร็จใน task นี้
- [ ] เขียนลง README ว่า **"reranking แก้ปัญหาการเรียงลำดับ ไม่ได้แก้ปัญหา candidate ที่หาไม่เจอตั้งแต่แรก"** — ถ้า recall ของ stage 1 ต่ำ rerank ช่วยอะไรไม่ได้เลย

## W7-4 — วัด trade-off ของ topN

**ทำ:** รัน topN = 5 / 10 / 20 / 50 แล้วทำตาราง latency vs quality

คาดว่าจะเห็น: topN สูง → recall เพดานสูงขึ้น (candidate เยอะขึ้น) แต่ latency โตเป็นเส้นตรง เพราะ cross-encoder เป็น O(N)

**DoD**
- [ ] ตาราง topN × (recall@5, MRR, latency) ครบทุกช่อง จากการรันจริง
- [ ] ระบุจุดที่ "คุ้มที่สุด" พร้อมเหตุผลจากตัวเลข
- [ ] เทียบกับ `router-fuse` (recall 0.92) ว่า **rerank + backend เดี่ยว ชนะ fuse ได้ไหม และถูกกว่าไหม**
