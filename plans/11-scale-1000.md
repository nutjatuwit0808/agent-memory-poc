# ส่วนขยาย — Scale test ที่ 1,000 ไฟล์ (ไม่ใช่ workshop ใหม่ในโครงนับเลข 01-10)

## คำถามตั้งต้น

- ตัวเลข recall/latency ที่วัดจาก vault 55 ไฟล์จริงยัง hold อยู่ไหมเมื่อ corpus ใหญ่ขึ้น 18 เท่า (1,000 ไฟล์)?
- UX จริงผ่าน Cursor/MCP เปลี่ยนไปแค่ไหนเมื่อมี "noise" (เอกสารที่ไม่เกี่ยวข้อง) ปนอยู่เยอะขึ้นมาก?
- เนื้อหาสังเคราะห์ที่เพิ่งสร้างเองค้นหาเจอจริงไหม (ไม่ใช่แค่วัดผลกระทบที่มันสร้างต่อ PayFlow query เดิม)?

## บริบท — สิ่งที่ทำไปแล้ว (เชิงปริมาณ, เสร็จแล้ว)

1. สร้าง vault synthetic distractor 945 ไฟล์ (15 โดเมนสมมติ ไม่เกี่ยวกับ payment/refund/order เลย เช่น warehouse-robotics, hr-onboarding, health-records) ผ่าน `src/cli/generate-synthetic-vault.ts` — vault เดิม 55 ไฟล์ + `bench/queries.json` **ไม่ถูกแตะเลย** รวมเป็น vault 1,000 ไฟล์
2. `npm run bench` (25 query เดิม, ground truth เดิม) — recall ตกทุก backend เมื่อมี distractor เข้ามา โดย vector ตกหนักสุด (0.78 → 0.63, -0.15) ส่วน router-fuse ยังสูงสุด (0.85)
3. `npm run bench:mcp` — cold start โต ~3 เท่า (615ms → 1,935ms) แต่ MCP overhead ยังต่ำมาก (1.5% → 4.4%)

ตัวเลขเต็มอยู่ในข้อความสรุปที่ให้ผู้ใช้ไปแล้วในเซสชันนี้ (ยังไม่ได้บันทึกลง CHECKLIST.md อย่างเป็นทางการ — รอทำพร้อมกับผลของ plan นี้)

**ช่องว่างที่ plan นี้จะปิด:** ตัวเลขข้างต้นมาจากการรัน script เท่านั้น ยังไม่เคยเห็นว่าตอนใช้งานจริงผ่าน Cursor (agent ตัดสินใจเรียก MCP tool เอง) ผลลัพธ์เปลี่ยนไปแค่ไหน และยังไม่เคยทดสอบว่าเนื้อหาสังเคราะห์เองค้นเจอไหม

## Decision points (ตัดสินแล้ว ตามที่คุยกับผู้ใช้)

| เรื่อง | ทางที่เลือก | เหตุผล |
|---|---|---|
| โหมด Cursor | **Agent mode** (ไม่ใช่ Ask mode แบบ W10-4) | รอบนี้ต้องการดูว่า agent เลือกเรียก MCP tool เองถูกจังหวะไหม ไม่ใช่วัด built-in indexing ของ Cursor เหมือน W10-4 |
| Workspace | ใช้โปรเจกต์ `agent-memory-poc` ตรงๆ (ไม่ isolate แบบ W10-4) | ไม่ได้วัด recall ของ Cursor built-in indexing รอบนี้ — วัดว่า MCP tool call ทำงานถูกไหมเท่านั้น ความเสี่ยง "เห็น bench/queries.json แล้วโกง" ที่เคยเจอใน W10-4 ไม่กระทบ methodology นี้ |
| MCP connection | ต้อง **reload** ก่อนเริ่ม (Configure memory-workshop → Reload) | process เดิมอาจ warm-up ค้างด้วย index ของ vault 55 ไฟล์เก่าในหน่วยความจำ ถ้าไม่ reload จะไม่เห็นไฟล์ใหม่เลย |

## Test cases

| # | Query | ประเภท | Baseline / สิ่งที่คาดหวัง |
|---|---|---|---|
| 1 | "ลูกค้าขอคืนเงินแล้วระบบค้าง ควรทำยังไง" | semantic, PayFlow (มี baseline จริงจาก W10-5) | ตอน 55 ไฟล์เคยได้ผลสมบูรณ์: `search_memory`×2, `get_memory`×3, ตอบตรง Case 2891/refund-timeout-policy/module-refund ครบ — เทียบว่ายังตรงเหมือนเดิมไหม จำนวน/ชื่อ tool call เปลี่ยนไหม |
| 2 | "PAYMENT_GATEWAY_TIMEOUT_MS คืออะไร" | exact identifier, PayFlow (ยังไม่เคยทดสอบผ่าน Cursor จริง มีแต่เลข bench) | bench บอกว่า exact-kind recall แทบไม่ตกที่ scale ใหญ่ (ripgrep/fts5 ยังแม่น) — ยืนยันผ่าน UI จริงว่า agent ยังหาไฟล์ถูกทั้ง 3 ไฟล์ (`env-variables-reference.md`, `connection-timeout-tuning.md`, `module-payment.md`) |
| 3 | "ทำไมหุ่นยนต์หยิบสินค้าไม่สำเร็จควร retry กี่ครั้ง" | semantic, **synthetic** (warehouse-robotics, ไม่มีใน bench queries เดิม) | ไม่มี baseline เชิงตัวเลข — เช็คว่า MCP หาเจอไหม ควรตอบอ้างอิง `pick-retry-policy` (MAX_PICK_RETRY_ATTEMPTS=2) จากโดเมน warehouse-robotics |
| 4 (bonus, ถ้ามีเวลา) | เลือก query จากโดเมนสังเคราะห์อื่นเพิ่ม เช่น "แพทย์เข้าถึงเวชระเบียนได้เมื่อไหร่" (health-records) | semantic, synthetic | เดียวกับข้อ 3 — ทดสอบ domain ที่ต่างออกไปอีกตัว |
