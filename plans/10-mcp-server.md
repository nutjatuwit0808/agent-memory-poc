# Workshop 10 — MCP server (ใช้ vault เป็น memory ใน Cursor)

## คำถามตั้งต้น

- ประสิทธิภาพที่วัดไว้ใน WS01–05 **ตามไปถึงตอนใช้ผ่าน Cursor จริงไหม** — หรือถูก overhead ของ protocol กลบ
- MCP protocol เพิ่มต้นทุนกี่ ms เทียบกับเรียก `serve.ts` ตรงๆ
- Cursor indexing (กล่องดำ) **ดึงเอกสารถูกกว่าหรือแย่กว่า** router ที่เราวัดไว้ว่า recall 0.87

## ทฤษฎีสั้น (เขียนลง README ตอนทำ)

MCP (Model Context Protocol) คือ JSON-RPC 2.0 ที่ทำให้ agent เรียก tool ภายนอกได้ — agent ตัดสินใจเองว่าจะเรียกเมื่อไหร่ แล้วเอาผลลัพธ์มาต่อเข้า context ก่อน generate ต่อ

**ต้นทุนที่ต่างจาก indexing ในตัว:** indexing ของ Cursor ทำงานอยู่ใน inference loop เดียวกัน แต่ MCP เป็น **round-trip แยกต่างหาก** (agent ตัดสินใจ → serialize → ส่ง → ประมวลผล → ส่งกลับ → ต่อ context) ซึ่งเป็นกลไกเดียวกับที่ WS05 วัดไว้แล้วว่า HTTP+JSON overhead ~15–20ms กลบความเร็ว 87 เท่าของ fts5 ให้เหลือ 3.2 เท่า — workshop นี้คือการวัดว่ากลไกเดิมนั้นเกิดซ้ำที่ชั้น MCP ด้วยหรือเปล่า

## ⚠️ สิ่งที่ workshop นี้วัดไม่ได้ (เขียนไว้ใน README ด้วย)

**Cursor indexing เป็นกล่องดำ** — วัด latency ภายในไม่ได้ ไม่รู้ว่า embed ที่ไหน ใช้โมเดลอะไร chunk ยังไง ดังนั้น:

- ❌ **ไม่เคลม** ว่า "MCP เร็วกว่า/ช้ากว่า Cursor indexing กี่เท่า" — วัดไม่ได้จริง
- ✅ **เคลมได้** ว่า MCP overhead ฝั่งเราเท่าไหร่ (วัดเองได้ทุก hop)
- ✅ **เคลมได้** ว่าฝั่งไหนดึงเอกสารถูกกว่า เพราะมี ground truth อยู่แล้วใน `bench/queries.json`

**ข้อจำกัดของการวัดคุณภาพฝั่ง Cursor:** สิ่งที่เห็นคือไฟล์ที่ Cursor **อ้างอิงในคำตอบ** ซึ่งคือ retrieval + การกรองของ LLM รวมกัน ไม่ใช่ recall ของ retrieval ล้วนๆ — ต้องเขียนกำกับไว้ทุกครั้งที่รายงานตัวเลขนี้ ห้ามเอาไปเทียบกับ recall@5 ของเราตรงๆ แบบไม่มีหมายเหตุ

## W10-2 — MCP server จริง

**ไฟล์:** `src/cli/mcp.ts` (ไฟล์ใหม่ ห้ามแก้ `serve.ts` หรือ backend เดิม)

**Tool ที่ expose (read-only ตาม D-12):**

| tool | พารามิเตอร์ | ทำอะไร |
|---|---|---|
| `search_memory` | `query`, `layer?`, `tags?`, `limit?`, `backend?` | ค้น vault คืน id + title + excerpt + score |
| `get_memory` | `id` | ดึงเนื้อหาเต็มของ note (เพราะ search คืนแค่ excerpt) |

**`backend` ต้อง optional และ default เป็น `router-route`** — คนใช้งานจริงไม่ควรต้องเลือกเอง (WS04 วัดแล้วว่า route ให้ recall 0.87 ที่ latency เกือบต่ำสุด) แต่ต้องบังคับเลือกได้เพื่อใช้ตอน benchmark

**Transport:** เสนอ **HTTP** ไม่ใช่ stdio เพราะ WS03 วัดไว้แล้วว่า cold start มีต้นทุนจริง (โหลดโมเดล ~1.3s + embed ทั้ง vault 4,543ms ถ้า cache เย็น + query แรก ~1,250ms จาก ONNX compile) ถ้าใช้ stdio Cursor จะ spawn process ใหม่ทุกครั้งที่เปิดโปรแกรม = จ่ายต้นทุนนี้ซ้ำทุกรอบ — **W10-3 จะวัดข้อนี้ให้เห็นเป็นตัวเลข ไม่ใช่เชื่อตามเหตุผล**

**DoD**
- [ ] ไม่แก้ไฟล์เดิมใน `src/` เลย (เพิ่ม `mcp.ts` อย่างเดียว) — ยืนยันด้วย mtime
- [ ] tool description เขียนให้ agent เข้าใจว่าควรเรียกเมื่อไหร่ (ไม่ใช่แค่ชื่อ tool)
- [ ] warm-up ครบก่อนรับ request แรก (ใช้แพตเทิร์นเดียวกับ `serve.ts`)
- [ ] error ที่ส่งกลับต้องอ่านรู้เรื่องในฝั่ง agent (เช่น `rg` ไม่มี, layer ผิด)
- [ ] รองรับทั้ง stdio และ HTTP เพื่อให้ W10-3 เทียบได้

## W10-3 — วัดต้นทุนฝั่งเรา (ส่วนที่วัดได้จริง)

**ทำ 2 การวัดที่แยกกัน:**

### (ก) MCP overhead ต่อ query

เขียน MCP client harness เล็กๆ ของเราเอง (ไม่ผ่าน Cursor เพื่อตัดตัวแปร LLM ออก) แล้วเทียบ 3 ชั้นกับ query ชุดเดียวกัน:

| ชั้น | วัดอะไร |
|---|---|
| `backend.search()` ตรงๆ | engine time ล้วน (มีตัวเลขจาก WS01–04 อยู่แล้ว) |
| HTTP ผ่าน `serve.ts` | + HTTP/JSON (WS05 วัดไว้ ~15–20ms) |
| MCP tool call | + MCP protocol |

**ส่วนต่างระหว่างชั้น 2 กับ 3 คือต้นทุนของ MCP ล้วนๆ** ซึ่งเป็นตัวเลขที่ยังไม่มีใครในโปรเจกต์นี้วัด

### (ข) Cold start — stdio vs HTTP

วัด "เวลาตั้งแต่ Cursor เริ่มจนได้คำตอบแรกที่ใช้ได้" ทั้งสอง transport

**DoD**
- [ ] ตาราง 3 ชั้น × query kind จากการรันจริง (warmup 3 + วัด 20 แบบเดียวกับ `bench.ts`)
- [ ] ระบุเป็นตัวเลขว่า MCP เพิ่มกี่ ms และคิดเป็นกี่ % ของ round-trip ทั้งหมด
- [ ] ตาราง cold start stdio vs HTTP — **ต้องตอบได้ว่าต่างกันจริงตามที่คาดใน W10-2 ไหม**
- [ ] เทียบกับบทเรียน WS05: overhead กลบความต่างของ engine ไปกี่เท่า

## W10-4 — เทียบคุณภาพกับ Cursor indexing

**Setup ที่ต้องบันทึกให้ทำซ้ำได้:** เปิดโฟลเดอร์ที่มี **แค่ `vault/`** ใน Cursor (ไม่ให้โค้ดในโปรเจกต์มารบกวน index) แล้วรอ indexing เสร็จ

**ทำ:** ยิง query ชุดเดียวกันสองทาง แล้วเทียบกับ `relevant` ใน `bench/queries.json`

- **ฝั่ง MCP:** อัตโนมัติ — คำนวณ recall@5 ได้เลยด้วยสูตรเดียวกับ `bench.ts`
- **ฝั่ง Cursor:** ทำมือ — ถามใน chat แล้วบันทึกว่าอ้างอิงไฟล์ไหนบ้าง

**เลือก query 10 ข้อพอ** (จาก 20 ข้อ) ให้ครบทุก kind — งานนี้ทำมือ ถ้าเอาครบ 20 จะไม่คุ้มเวลาและมีโอกาสทำครึ่งทางแล้วเลิก

**DoD**
- [ ] ตารางเทียบ 10 query — ฝั่งเรา recall@5 vs ฝั่ง Cursor "อ้างอิงไฟล์ถูกกี่ไฟล์"
- [ ] **เขียนกำกับทุกตัวเลขฝั่ง Cursor** ว่าเป็น retrieval + การกรองของ LLM รวมกัน ไม่ใช่ recall ล้วน
- [ ] บันทึก setup ให้ทำซ้ำได้: Cursor version, โหมดที่ใช้ (`@codebase`/`@docs`/agent), รอ index นานแค่ไหน
- [ ] ยกเคสจริงอย่างน้อย 2 เคสที่ผลต่างกันชัด **พร้อมเดาสาเหตุจากสิ่งที่เรารู้เรื่อง chunking/tokenizer จาก WS02–03**
- [ ] ถ้า Cursor ชนะในบางเคส **ต้องรายงานตรงๆ** ไม่ใช่เลือกเฉพาะเคสที่เราชนะ

## W10-5 — Packaging + จัดการ index stale (ส่วน "ใช้งานจริง")

**ทำ:** ทำให้ติดตั้งแล้วใช้ได้จริงโดยไม่ต้องอ่านโค้ด

**ปัญหา stale ที่ต้องแก้จริงจัง:** WS02 พิสูจน์ไว้แล้วว่าแก้ไฟล์ใน vault แล้ว index ไม่รู้ตัว — ถ้าใช้เป็น memory ทุกวัน **agent จะได้คำตอบเก่าแบบเงียบๆ** ซึ่งอันตรายกว่าตอนรัน bench เพราะไม่มีใครสังเกต

ทางเลือก (ต้องเลือกและบันทึกเหตุผล): auto-reindex ตอน startup · เช็ค `checkStale()` แล้วแนบคำเตือนไปกับผลลัพธ์ · file watcher

**DoD**
- [ ] มีตัวอย่าง `.cursor/mcp.json` ที่ก๊อปไปใช้ได้เลย
- [ ] เอกสารบอกขั้นตอนตั้งแต่ `npm install` จนถามใน Cursor ได้
- [ ] จัดการ stale ได้จริง — ทดสอบโดยแก้ไฟล์ใน vault แล้วถามใหม่ ต้องไม่ได้คำตอบเก่าแบบเงียบๆ
- [ ] preflight ครบ (rg ไม่มี / โมเดลยังไม่โหลด / index ยังไม่ build) พร้อม error ที่บอกวิธีแก้
- [ ] ลองใช้จริงอย่างน้อย 1 วันทำงาน แล้วจดว่าติดขัดตรงไหน
