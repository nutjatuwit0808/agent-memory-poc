# วงจรชีวิตของการชำระเงินแบบละเอียด (Payment Lifecycle — Full Reference)

เอกสารนี้รวบรวมทุกสถานะ ทุก transition และทุก edge case ของการชำระเงินในระบบ PayFlow ไว้ในที่เดียว เขียนขึ้นเพราะทีมพบว่าความรู้เรื่องนี้กระจัดกระจายอยู่ในหัวของวิศวกรหลายคน เวลามีปัญหาเกิดขึ้นแต่ละคนจะเข้าใจ flow ไม่ตรงกัน เอกสารนี้จึงตั้งใจเขียนให้ละเอียดที่สุดเท่าที่จะทำได้ เพื่อเป็นแหล่งอ้างอิงเดียวที่ทุกคนเชื่อถือได้

## ภาพรวมของสถานะทั้งหมด

การชำระเงินหนึ่งครั้งมีสถานะที่เป็นไปได้ดังนี้: `initiated`, `authorizing`, `authorized`, `capturing`, `captured`, `failed`, `reversed`, `partially_reversed` แต่ละสถานะมีความหมายและเงื่อนไขการเข้า-ออกที่ต่างกัน

### initiated

เกิดขึ้นทันทีที่ order-service เรียก `chargePayment(orderId, amount, method)` (ดูรายละเอียด signature ที่ [[structure/module-payment]]) payment-service สร้าง record การชำระเงินในสถานะนี้ก่อนที่จะติดต่อ gateway ภายนอกด้วยซ้ำ เหตุผลที่ต้องมีสถานะนี้แยกจาก `authorizing` คือเพื่อให้มี record อยู่ในระบบแม้ request ไปยัง gateway จะยังไม่ถูกส่งเลยก็ตาม ถ้าเกิด crash ระหว่างขั้นตอนนี้ ระบบจะรู้ว่ามีความพยายามชำระเงินที่ยังไม่เสร็จสมบูรณ์อยู่ และสามารถ query กลับมาดูได้ว่าติดอยู่ตรงไหน

### authorizing

เกิดขึ้นเมื่อ request ถูกส่งไปยัง payment gateway แล้ว กำลังรอผลลัพธ์ ระยะเวลาที่อยู่ในสถานะนี้ปกติไม่เกินไม่กี่วินาที เว้นแต่ gateway มีปัญหา ถ้าอยู่ในสถานะนี้เกิน `GATEWAY_TIMEOUT_MS` (ค่าเริ่มต้น 30 วินาที) ระบบจะยกเลิกการรอและเปลี่ยนเป็น `failed` พร้อม error code `PAYMENT_GATEWAY_TIMEOUT` แต่สิ่งสำคัญที่ต้องเข้าใจคือ **การที่ระบบเราถือว่า timeout ไม่ได้แปลว่าฝั่ง gateway ไม่ได้ authorize เงินจริง** เป็นไปได้ที่ gateway authorize สำเร็จแต่ response กลับมาช้ากว่าที่เรารอไหว นี่คือเหตุผลที่ต้องมีฟังก์ชัน `verifyPayment(paymentId)` แยกต่างหาก เพื่อ query สถานะจริงจาก gateway ย้อนหลังเมื่อไม่แน่ใจ

### authorized

gateway ยืนยันว่าวงเงินถูกกันไว้แล้ว (authorization hold) แต่เงินยังไม่ถูกตัดออกจากบัญชีลูกค้าจริง ระบบ PayFlow ใช้โมเดล authorize-then-capture แยกสองขั้นตอนแทนที่จะตัดเงินทันทีทีเดียว เหตุผลคือทำให้สามารถยกเลิกได้ก่อนตัดเงินจริงในกรณีที่ order ถูกยกเลิกในช่วงเวลาสั้นๆ ก่อนจัดส่ง (ดู [[business-logic/order-cancellation-policy]] เกี่ยวกับกรอบเวลาที่ยกเลิกได้)

authorization hold มีอายุจำกัดตามที่ผู้ออกบัตรกำหนด โดยทั่วไปประมาณ 7 วัน ถ้าระบบไม่ capture ภายในเวลานี้ hold จะหมดอายุอัตโนมัติที่ฝั่งธนาคาร และต้อง authorize ใหม่ทั้งหมด

### capturing / captured

เมื่อ order พร้อมสำหรับการตัดเงินจริง (ปกติคือทันทีที่ authorize สำเร็จสำหรับ digital goods หรือหลัง inventory ถูกยืนยันสำหรับสินค้าจริง) ระบบจะเรียก capture ไปยัง gateway `captured` คือสถานะสุดท้ายที่ถือว่าเงินโอนสำเร็จ นับจากจุดนี้ order-service จะได้รับ event และเปลี่ยนสถานะ order เป็น `paid`

สิ่งที่ทีมเรียนรู้จากเหตุการณ์จริง: การ capture ล้มเหลวหลังจาก authorize สำเร็จเป็นกรณีที่หายากแต่ทำให้เกิดปัญหาซับซ้อนที่สุด เพราะ authorization hold ยังคาราคาซังอยู่ที่บัญชีลูกค้า แต่ order ในระบบเรายังไม่ได้ถูกมองว่า paid — ถ้าไม่มี job คอยตรวจสอบ authorization ที่ค้างนาน ลูกค้าจะเห็นเงินถูกกันไว้โดยไม่รู้สาเหตุ ระบบจึงมี background job รันทุก 1 ชั่วโมงเพื่อหา authorization ที่ค้างเกิน 6 ชั่วโมงแล้วยังไม่ capture และแจ้งเตือนทีมให้ตรวจสอบ

### failed

เกิดได้จากหลายสาเหตุ: `PAYMENT_DECLINED` (บัตรถูกปฏิเสธจากธนาคารผู้ออกบัตร), `PAYMENT_GATEWAY_TIMEOUT` (ระบบเรารอ response นานเกินไป), หรือ `PAYMENT_GATEWAY_ERROR` (gateway ตอบกลับมาเป็น error ที่ไม่ใช่การปฏิเสธจากธนาคาร เช่น internal error ฝั่ง gateway เอง)

ความแตกต่างสำคัญระหว่างสามกรณีนี้คือนโยบายการ retry: `PAYMENT_DECLINED` จะไม่ retry อัตโนมัติเด็ดขาดเพราะเป็นการตัดสินใจของธนาคารที่ retry ซ้ำก็ได้ผลเหมือนเดิม ส่วนอีกสองกรณีถือเป็นปัญหาชั่วคราวที่ retry ได้ตามนโยบายใน [[business-logic/payment-retry-policy]] การแยกแยะสามกรณีนี้ให้ถูกต้องตั้งแต่ต้นทางสำคัญมาก เพราะถ้า retry กรณี `PAYMENT_DECLINED` ผิดพลาดซ้ำๆ อาจทำให้ธนาคารสงสัยว่าบัตรลูกค้าถูกขโมยและ block บัตรนั้นชั่วคราว ซึ่งเป็นผลเสียที่หนักกว่าการชำระเงินไม่สำเร็จครั้งเดียว

### reversed / partially_reversed

เกิดขึ้นเมื่อ refund-service เรียก endpoint ภายใน `reversePayment(paymentId, amount)` เพื่อคืนเงินตามที่อธิบายไว้ใน [[structure/module-refund]] ถ้าจำนวนเงินที่คืนเท่ากับยอด capture เดิมทั้งหมด สถานะจะเป็น `reversed` แต่ถ้าคืนบางส่วน (partial refund กรณีคืนเฉพาะบางรายการใน order เดียวกัน) สถานะจะเป็น `partially_reversed` และยังสามารถถูกเรียก reverse เพิ่มได้อีกจนกว่าจะครบยอดเดิม

ข้อจำกัดสำคัญ: ไม่สามารถ reverse เกินยอดที่ capture ไปแล้วได้ไม่ว่ากรณีใด ถ้ามีความพยายามเรียก `reversePayment` ด้วยยอดที่เกินยอดคงเหลือที่ยัง reverse ได้ ระบบจะปฏิเสธทันทีด้วย error โดยไม่แตะยอดเงินใดๆ เลย เพื่อป้องกันการคืนเงินเกินจริงอย่างเด็ดขาด

## ความสัมพันธ์ระหว่าง payment lifecycle กับ order lifecycle

สิ่งที่วิศวกรใหม่มักสับสนคือคิดว่า payment status กับ order status เป็นตัวเดียวกัน แต่จริงๆ แล้วเป็นสอง state machine ที่แยกจากกันโดยสิ้นเชิงและสื่อสารกันผ่าน event เท่านั้น (ตามหลักการ service boundary ที่อธิบายใน [[structure/overview-architecture]]) ตารางด้านล่างแสดงความสัมพันธ์คร่าวๆ ระหว่างสองระบบ แต่ไม่ใช่ mapping แบบตรงตัวเสมอไป:

- payment `captured` มักตรงกับ order เปลี่ยนเป็น `paid` แต่ไม่ใช่เสมอไป เพราะ order-service รอ event และอาจมี delay เล็กน้อยจาก message queue
- payment `reversed` ตรงกับ order เปลี่ยนเป็น `refunded` ก็ต่อเมื่อเป็นการ reverse เต็มจำนวนเท่านั้น ถ้าเป็น `partially_reversed` order จะยังคงสถานะเดิมและมีแค่ field แยกต่างหากบันทึกว่ามีการคืนเงินบางส่วนเกิดขึ้น

## Fraud check เกิดขึ้นตอนไหนในวงจรนี้

fraud detection (ดู [[business-logic/fraud-detection-rules]]) ทำงานคู่ขนานกับขั้นตอน `authorizing` ไม่ใช่ก่อนหรือหลัง หากระบบตรวจพบสัญญาณผิดปกติระหว่างรอผล authorize จาก gateway การชำระเงินจะถูก mark เป็น `flagged` เพิ่มเติมจากสถานะปกติ (เป็น flag คู่ขนาน ไม่ใช่สถานะแทนที่) และหยุดกระบวนการ capture อัตโนมัติไว้จนกว่าทีม risk จะตรวจสอบ แม้ authorize จาก gateway จะสำเร็จแล้วก็ตาม

การออกแบบให้ fraud check ทำงานคู่ขนานแทนที่จะเป็นขั้นตอนก่อนหน้า (pre-check) เป็นการตัดสินใจที่ตั้งใจ เพราะการรอผล fraud check ก่อนจะส่ง request ไปยัง gateway จะทำให้ latency ของการชำระเงินโดยรวมสูงขึ้นสำหรับผู้ใช้ทุกคน ทั้งที่ผู้ใช้ส่วนใหญ่ไม่มีปัญหาอะไรเลย การทำคู่ขนานทำให้ประสบการณ์ของผู้ใช้ทั่วไปไม่ช้าลง ในขณะที่ยังจับกรณีผิดปกติได้ทันเวลาก่อนเงินจะถูกตัดจริง

## บทเรียนจากเหตุการณ์จริงที่เกี่ยวกับ lifecycle นี้

มีอยู่ครั้งหนึ่งที่ gateway ตอบ authorize สำเร็จแต่ webhook ยืนยันมาถึงช้ากว่าปกติมาก (เกิน 20 นาที) ระหว่างนั้นระบบของเรายังคงสถานะเป็น `authorizing` อยู่ และเนื่องจากยังไม่ถึง `GATEWAY_TIMEOUT_MS` ที่กำหนดไว้แค่ 30 วินาที ระบบจึงเปลี่ยนเป็น `failed` ไปก่อนที่ webhook จริงจะมาถึง ทำให้เกิดสถานการณ์ที่เงินถูก authorize จริงที่ฝั่งธนาคารแล้ว แต่ระบบของเราคิดว่าล้มเหลว และมีความพยายาม retry เพิ่มเข้าไปอีก ซึ่งเกือบทำให้ลูกค้าถูกตัดเงินสองครั้ง

เหตุการณ์นี้เป็นที่มาของการเพิ่มขั้นตอนตรวจสอบก่อน retry ทุกครั้ง: ก่อนที่ระบบจะ initiate การชำระเงินใหม่สำหรับ order เดิม จะต้องเรียก `verifyPayment` กับ payment ที่ `failed` ก่อนเสมอเพื่อยืนยันว่า gateway ไม่ได้ authorize เงินไว้จริงๆ แล้ว ขั้นตอนนี้เพิ่ม latency เล็กน้อยให้กับ retry flow แต่ทีมเห็นตรงกันว่าความถูกต้องสำคัญกว่าความเร็วในจุดนี้ เพราะผลของการตัดเงินซ้ำสร้างความเสียหายต่อความเชื่อมั่นของลูกค้ามากกว่าความช้าที่แทบสังเกตไม่ได้ของ retry อีกไม่กี่วินาที

## สรุปสำหรับคนที่ debug ปัญหาเกี่ยวกับ payment

เมื่อเจอปัญหาการชำระเงินที่ดูแปลกๆ ให้ตั้งคำถามตามลำดับนี้เสมอ: สถานะปัจจุบันคืออะไร, transition ล่าสุดเกิดขึ้นเมื่อไหร่และเพราะอะไร (ดู log ตาม [[convention/logging-convention]] ซึ่งมี `requestId` และ `paymentId` ติดตามได้เสมอ), และสถานะนี้สอดคล้องกับสถานะจริงที่ gateway หรือไม่ (เรียก `verifyPayment` เพื่อ cross-check) การข้ามขั้นตอนใดขั้นตอนหนึ่งในสามข้อนี้คือสาเหตุหลักที่ทำให้การ debug ปัญหาการชำระเงินใช้เวลานานเกินความจำเป็น

## ภาคผนวก: คำถามที่พบบ่อยเกี่ยวกับวงจรชีวิตการชำระเงิน

ส่วนนี้รวบรวมคำถามที่ทีมใหม่ถามซ้ำๆ บ่อยที่สุดเกี่ยวกับ payment lifecycle พร้อมคำตอบละเอียด เพื่อลดภาระของวิศวกรอาวุโสที่ต้องอธิบายเรื่องเดิมซ้ำทุกครั้งที่มีคนเข้าทีมใหม่

### ทำไมไม่ตัดเงินทันทีทีเดียวโดยไม่ต้องมีขั้นตอน authorize แยกจาก capture

คำถามนี้มาจากคนที่คุ้นเคยกับระบบชำระเงินแบบง่ายที่ตัดเงินทันทีตอนกดยืนยัน คำตอบคือ PayFlow เลือกโมเดล authorize-then-capture เพราะสินค้าจริงต้องผ่านขั้นตอนแพ็คและตรวจสอบสต็อกก่อนที่จะยืนยันได้แน่นอนว่าจะส่งได้จริง การตัดเงินทันทีแล้วค่อยพบว่าสินค้าหมดสต็อกจะสร้างภาระงานคืนเงินที่ไม่จำเป็น ในขณะที่การกันวงเงินไว้ก่อนแล้วค่อย capture เมื่อพร้อมส่งจริงทำให้ยกเลิกได้ง่ายกว่ามากในกรณีที่มีปัญหาเกิดขึ้นก่อนสินค้าจะออกจากคลัง ข้อเสียคือความซับซ้อนของระบบเพิ่มขึ้น แต่ทีมประเมินว่าคุ้มค่ากับความยืดหยุ่นที่ได้มา

### ถ้า authorization hold หมดอายุก่อนที่จะ capture จะเกิดอะไรขึ้น

กรณีนี้เกิดขึ้นได้จริงถ้า order ค้างอยู่ในขั้นตอนรอแพ็คนานเกิน 7 วัน (พบน้อยมากในทางปฏิบัติเพราะกระบวนการปกติเร็วกว่านั้นมาก แต่เคยเกิดกับสินค้าพิเศษที่ต้องสั่งผลิตตามคำขอ) เมื่อ capture ล้มเหลวเพราะ hold หมดอายุ ระบบจะพยายาม authorize ใหม่โดยอัตโนมัติหนึ่งครั้ง ถ้าบัตรลูกค้ายังใช้งานได้และมีวงเงินพอ การ authorize ใหม่จะสำเร็จและกระบวนการเดินหน้าต่อได้โดยลูกค้าไม่ต้องทำอะไรเพิ่ม แต่ถ้า authorize ใหม่ล้มเหลว (เช่นบัตรหมดอายุไปแล้วในช่วงเวลานั้นพอดี) order จะถูกแจ้งเตือนให้ลูกค้าอัปเดตวิธีชำระเงินก่อนดำเนินการต่อ

### เหตุใดการ reverse บางส่วน (partial reversal) จึงซับซ้อนกว่าที่คิด

เมื่อ order หนึ่งใบมีสินค้าหลายรายการและลูกค้าต้องการคืนเงินเฉพาะบางรายการ ระบบต้องคำนวณสัดส่วนของค่าจัดส่งและส่วนลดที่เคยให้ไปแล้วอย่างถูกต้องด้วย ไม่ใช่แค่หักราคาสินค้ารายการนั้นตรงๆ ตัวอย่างเช่น ถ้า order ได้รับส่วนลดแบบเปอร์เซ็นต์ (ดู [[business-logic/promo-code-rules]]) การคืนเงินบางส่วนต้องคืนในสัดส่วนเดียวกันของส่วนลดนั้นด้วย ไม่ใช่คืนราคาเต็มของสินค้ารายการนั้นก่อนหักส่วนลด มิฉะนั้นร้านค้าจะขาดทุนเกินความเป็นจริงจากส่วนต่างของส่วนลดที่คำนวณผิด

### ทำไมสถานะ `captured` ถึงไม่สามารถย้อนกลับไปเป็น `authorized` ได้อีก

การออกแบบ state machine ของ payment เป็นแบบ forward-only อย่างเคร่งครัดในทิศทางหลัก เพราะการยอมให้ย้อนสถานะกลับจะเปิดช่องให้เกิดความสับสนว่าเงินถูกตัดจริงหรือไม่ ณ เวลาใดเวลาหนึ่ง ถ้าต้องการยกเลิกเงินที่ capture ไปแล้ว ระบบบังคับให้ผ่านขั้นตอน reverse เท่านั้น ซึ่งสร้าง record ใหม่ที่อ้างอิงกลับไปยัง payment เดิมอย่างชัดเจน แทนที่จะแก้ไข record เดิมให้ดูเหมือนไม่เคย capture มาก่อน หลักการนี้ทำให้ audit trail ของทุกการชำระเงินสมบูรณ์และตรวจสอบย้อนหลังได้เสมอ ซึ่งสำคัญมากทั้งสำหรับการทำบัญชีและสำหรับการสืบสวนกรณีข้อพิพาทตาม [[business-logic/dispute-resolution-process]]

### จะรู้ได้อย่างไรว่าการ retry ครั้งถัดไปปลอดภัยไม่ทำให้ตัดเงินซ้ำ

นี่คือคำถามที่สำคัญที่สุดสำหรับวิศวกรที่ต้อง debug ปัญหาการชำระเงิน คำตอบสั้นๆ คือห้าม retry โดยไม่ตรวจสอบสถานะจริงจาก gateway ก่อนเสมอไม่ว่ากรณีใด ตามที่อธิบายไว้ในหัวข้อบทเรียนจากเหตุการณ์จริงข้างต้น ระบบมีการป้องกันอีกชั้นหนึ่งด้วย idempotency key ที่ส่งไปพร้อมทุก request การชำระเงิน — gateway ที่รองรับ idempotency key จะปฏิเสธการตัดเงินซ้ำถ้า key เดิมถูกส่งมาอีกครั้งภายในหน้าต่างเวลาที่กำหนด (24 ชั่วโมง) เป็นการป้องกันสองชั้นที่ทำงานร่วมกัน ทั้งจากฝั่งตรรกะของระบบเราเองและจากฝั่ง gateway
