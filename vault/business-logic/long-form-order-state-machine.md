# State Machine ของ Order แบบละเอียด (Full Reference)

เอกสารนี้อธิบายทุกสถานะและทุก transition ของ order ในระบบ PayFlow อย่างละเอียด เขียนขึ้นหลังจากทีมพบว่ามีการตีความ state machine ผิดกันหลายครั้งระหว่างทีม frontend, backend และ support จนทำให้เกิดบั๊กที่ order ค้างอยู่ในสถานะที่ไม่ควรเป็นไปได้ตาม logic เอกสารนี้จึงตั้งใจให้ครอบคลุมทุก edge case เท่าที่ทีมเคยเจอมา

## รายชื่อสถานะทั้งหมด

`created`, `paid`, `packed`, `shipped`, `delivered`, `cancelled`, `refunding`, `refunded`, `disputed`, `payment_failed`

## created

สถานะแรกสุด เกิดขึ้นทันทีที่ `createOrder(cart, customerId)` (ดู [[structure/module-order]]) ทำงานสำเร็จ ซึ่งหมายความว่าการกันสต็อกผ่าน `reserveStock` (ดูรายละเอียดที่ [[business-logic/inventory-reservation-rules]]) สำเร็จแล้วเช่นกัน — order จะไม่ถูกสร้างเลยถ้ากันสต็อกไม่สำเร็จ ดังนั้นการที่ order อยู่ในสถานะ `created` แปลว่ามีสต็อกถูกกันไว้ให้แน่นอน

จุดสำคัญที่ต้องเข้าใจ: สถานะนี้ไม่ได้แปลว่าลูกค้าชำระเงินแล้ว เป็นเพียงขั้นตอนกันที่นั่ง (เปรียบเทียบง่ายๆ) ไว้ก่อนที่จะไปขั้นตอนชำระเงินจริง ถ้าลูกค้าไม่ชำระเงินภายใน 15 นาที (อายุของ reservation) สต็อกจะถูกปล่อยคืนอัตโนมัติ แต่ order เองจะไม่ถูกลบทิ้ง เพียงแต่จะไม่มีทางเปลี่ยนเป็น `paid` ได้อีกต่อไปเพราะสต็อกไม่ได้ถูกกันไว้แล้ว ถ้าลูกค้าพยายามชำระเงินหลังจากนั้นระบบจะแจ้งว่าต้องสั่งซื้อใหม่

## paid

เกิดขึ้นเมื่อ order-service ได้รับ event ยืนยันจาก payment-service ว่าการชำระเงิน `captured` สำเร็จ (ดูรายละเอียดฝั่ง payment ที่ [[business-logic/long-form-payment-lifecycle]]) ทันทีที่เข้าสถานะนี้ ระบบจะเรียก `commitStock` เพื่อตัดสต็อกจริงแทนที่การกันสต็อกชั่วคราว และส่ง notification `order-confirmed` หาลูกค้า

หมายเหตุสำคัญ: การเปลี่ยนจาก `created` เป็น `paid` ไม่ได้เกิดแบบ synchronous กับ request ของลูกค้าเสมอไป เพราะขึ้นอยู่กับ event จาก message queue (ดู [[structure/queue-architecture]]) ซึ่งอาจมี delay เล็กน้อย ทีม frontend เคยเจอปัญหาที่ลูกค้า refresh หน้าเร็วเกินไปหลัง checkout แล้วเห็น order ยังเป็น `created` ทั้งที่จ่ายเงินสำเร็จแล้วจริง จึงต้องเพิ่ม polling พร้อม loading state ที่บอกลูกค้าว่า "กำลังยืนยันการชำระเงิน" แทนที่จะแสดงผลทันที

## packed

ทีมคลังสินค้าเปลี่ยนสถานะนี้เองผ่านระบบจัดการคลัง (ไม่ใช่ automatic transition) เมื่อสินค้าถูกแพ็คพร้อมส่งจริง สถานะนี้สำคัญมากในบริบทของนโยบายยกเลิก เพราะเป็นเส้นแบ่งที่ [[business-logic/order-cancellation-policy]] ใช้ตัดสินว่าลูกค้ายังยกเลิกเองผ่านแอปได้หรือไม่ — ก่อน `packed` ยกเลิกเองได้ทันที หลังจากนี้ต้องติดต่อ support

Race condition ที่เคยเกิดขึ้นจริง: ลูกค้ากดยกเลิกในเสี้ยววินาทีเดียวกับที่ทีมคลังกด mark เป็น `packed` พอดี ระบบจัดการด้วยการใช้ database transaction แบบ compare-and-swap บน field สถานะ — ใครก็ตามที่เขียนสถานะสำเร็จก่อนจะชนะ อีกฝั่งจะได้ error และต้องแสดงข้อความที่เหมาะสม (ถ้าคลังชนะ: แจ้งลูกค้าว่ายกเลิกเองไม่ได้แล้วให้ติดต่อ support, ถ้าลูกค้าชนะ: แจ้งทีมคลังว่า order นี้ถูกยกเลิกแล้วห้ามแพ็ค)

## shipped

ระบบขนส่งภายนอกส่ง webhook เข้ามาเมื่อพัสดุถูกรับเข้าระบบขนส่งแล้ว สถานะนี้มาพร้อม tracking number ที่ถูกส่งต่อให้ลูกค้าผ่าน notification

จุดที่ทีมเคยพลาด: ในช่วงแรกของระบบ ยอมให้ transition จาก `paid` ตรงไปยัง `shipped` ได้เลยถ้า webhook จากขนส่งมาถึงเร็วกว่าที่คลังจะกด `packed` ในระบบภายใน (เพราะเป็นคนละระบบที่ไม่ได้ sync กันแบบ real-time) ทำให้เกิด order ที่ "ข้าม" สถานะ `packed` ไปเลย ซึ่งพังเงื่อนไขการยกเลิกที่อ้างอิงสถานะ `packed` เป็นเส้นแบ่ง ภายหลังแก้โดยบังคับว่า order ต้องผ่าน `packed` ก่อนเท่านั้นถึงจะรับ webhook `shipped` ได้ ถ้า webhook มาถึงก่อนจะถูก queue รอไว้ไม่ apply ทันที

## delivered

ขนส่งยืนยันว่าส่งถึงมือลูกค้าแล้ว นับจากจุดนี้เริ่มนับ 7 วันสำหรับสิทธิ์คืนเงินแบบเต็มจำนวนตาม [[business-logic/refund-policy]] และเริ่มนับถอยหลังสำหรับการเข้าคะแนนสะสมตามที่อธิบายไว้ในเอกสารเรื่องคะแนนสะสม

## cancelled

เข้าถึงได้จาก `created` หรือ `paid` เท่านั้น (ก่อน `packed`) ถ้ายกเลิกตอนยัง `created` ไม่มีเงินถูกตัดไปเลยเพียงแค่ปล่อยสต็อกคืน ถ้ายกเลิกตอน `paid` ระบบจะเรียก reverse การชำระเงินอัตโนมัติแบบเต็มจำนวนทันทีโดยไม่ต้องรอการอนุมัติ (ต่างจากกรณี refund ปกติที่มูลค่าสูงต้องรออนุมัติ) เพราะถือว่ายังไม่มีต้นทุนการจัดส่งเกิดขึ้นเลย

## refunding / refunded

แยกออกจาก `cancelled` โดยสิ้นเชิง — สองสถานะนี้ใช้เมื่อ order ผ่าน `packed` ไปแล้ว การคืนเงินในกรณีนี้ต้องผ่านกระบวนการตรวจสอบสินค้าตามเงื่อนไขใน [[business-logic/refund-policy]] จึงมีสถานะระหว่างทาง `refunding` แยกจาก `refunded` ที่เป็นสถานะสุดท้าย ระยะเวลาที่อยู่ใน `refunding` ขึ้นอยู่กับว่าต้องรอตรวจสอบสินค้าหรือรออนุมัติจากทีม support หรือไม่

## disputed

เกิดจาก webhook แจ้ง chargeback จากธนาคาร ไม่ใช่ transition ปกติที่มาจากการกระทำของลูกค้าโดยตรงในระบบ สามารถเกิดขึ้นได้จากเกือบทุกสถานะที่ผ่าน `paid` มาแล้ว และไม่ได้แทนที่สถานะเดิม แต่เป็น flag คู่ขนานคล้ายกับ fraud flag ที่อธิบายไว้ในเอกสารเรื่องวงจรการชำระเงิน order ยังคงเดินหน้าตาม flow ปกติ (เช่น ยังคงจัดส่งต่อไปถ้ากำลังอยู่ระหว่างทาง) ในขณะที่ทีม support จัดการข้อพิพาทคู่ขนานกันไป

## payment_failed

เข้าได้จาก `created` เท่านั้น เมื่อการชำระเงินล้มเหลวครบทุกครั้งที่ retry ได้แล้วตามนโยบาย order ในสถานะนี้จะไม่ถือครองสต็อกอีกต่อไป (ถูกปล่อยคืนไปพร้อมกับที่ payment ล้มเหลว) ลูกค้าสามารถลองสั่งซื้อใหม่ได้ แต่ order เดิมจะไม่ถูกนำกลับมาใช้ใหม่ ระบบสร้าง order ใหม่ทั้งหมดเสมอเมื่อลองอีกครั้ง เพื่อให้แต่ละ order สื่อถึงความพยายามชำระเงินหนึ่งครั้งอย่างชัดเจนไม่คลุมเครือ

## แผนภาพ transition โดยสรุป

```
created --(ชำระเงินสำเร็จ)--> paid
created --(ชำระเงินล้มเหลวครบ retry)--> payment_failed
created --(ยกเลิก / reservation หมดอายุ)--> cancelled
paid --(ทีมคลังแพ็ค)--> packed
paid --(ยกเลิก)--> cancelled (reverse เงินอัตโนมัติ)
packed --(รับเข้าขนส่ง)--> shipped
shipped --(ยืนยันถึงมือลูกค้า)--> delivered
packed/shipped/delivered --(คำขอคืนเงินได้รับอนุมัติ)--> refunding --> refunded
(เกือบทุกสถานะหลัง paid) --(ธนาคารแจ้ง chargeback)--> ติด flag disputed คู่ขนาน
```

## ทำไมต้องเขียนละเอียดขนาดนี้

state machine ที่ดูเรียบง่ายบนกระดาษมักซ่อน edge case จำนวนมากไว้เมื่อนำไปใช้งานจริงกับระบบที่มีหลาย service ทำงานแบบ asynchronous พร้อมกัน ทีมเชื่อว่าการเขียนทุก edge case ที่เคยเจอไว้เป็นลายลักษณ์อักษร ดีกว่าปล่อยให้เป็นความรู้ที่อยู่ในหัวคนไม่กี่คน เพราะทุกครั้งที่มีคนใหม่เข้าทีมหรือมีคนลาออก ความรู้แบบปากเปล่านี้มักหายไปพร้อมกับตัวคน จนต้องมาเจอปัญหาเดิมซ้ำแล้วซ้ำเล่า

## ภาคผนวก: edge case เพิ่มเติมที่ทีมเคยเจอ

### order ที่ลูกค้ายกเลิกแต่ระบบขนส่งส่งของมาส่งจริง

เคยเกิดกรณีที่ลูกค้ายกเลิกรายการสำเร็จตอน order ยังเป็นสถานะ `paid` (ก่อน `packed` ตามเงื่อนไขปกติ) แต่ด้วยความล่าช้าของการ sync ข้อมูลระหว่างระบบภายในกับระบบคลังสินค้าที่เป็น vendor ภายนอก ทำให้พนักงานคลังยังคงแพ็คและส่งสินค้าออกไปจริงก่อนที่คำสั่งยกเลิกจะไปถึง เมื่อพัสดุไปถึงมือลูกค้าที่ยกเลิกไปแล้ว ทีม support ต้องประสานงานให้ลูกค้าปฏิเสธรับพัสดุหรือส่งคืนโดยไม่มีค่าใช้จ่าย และเงินที่ reverse ไปแล้วตอนยกเลิกจะไม่ถูกเรียกเก็บซ้ำ เหตุการณ์นี้นำไปสู่การเพิ่มขั้นตอนตรวจสอบสถานะกับระบบคลังภายนอกแบบ real-time มากขึ้นก่อนจะอนุญาตให้ยกเลิกอัตโนมัติสำเร็จ

### order ที่ค้างในสถานะ created นานผิดปกติโดยไม่มีการ interaction จากลูกค้า

ปกติ order ในสถานะ `created` ควรเปลี่ยนสถานะภายใน 15 นาที (อายุของการกันสต็อก) แต่มีบางกรณีที่ order ค้างอยู่นานหลายชั่วโมงโดยไม่มี log แสดงว่ามีความพยายามชำระเงินเกิดขึ้นเลย ตรวจสอบพบว่าเป็นผลจาก background job ที่ควรจะปล่อยสต็อกคืนเมื่อ reservation หมดอายุทำงานผิดพลาดชั่วคราวในบาง batch ทำให้ order ไม่ถูกเปลี่ยนเป็น `payment_failed` ตามที่ควรจะเป็น ทีมแก้ปัญหาด้วยการเพิ่ม monitoring แยกต่างหากสำหรับนับจำนวน order ที่ค้างในสถานะ `created` เกิน 30 นาที เพื่อจับความผิดปกติของ background job ได้เร็วขึ้นในอนาคต

### ความสัมพันธ์ระหว่างสถานะ order กับสถานะการจอง promotion

order ที่ใช้โค้ดส่วนลดแบบมีจำนวนจำกัด (เช่น "100 สิทธิ์แรกเท่านั้น") จะกันสิทธิ์การใช้โค้ดไว้ทันทีที่ order เข้าสถานะ `created` เช่นเดียวกับการกันสต็อกสินค้า ถ้า order ไม่ไปต่อและถูกปล่อยคืนเนื่องจาก reservation หมดอายุ สิทธิ์การใช้โค้ดจะถูกปล่อยคืนพร้อมกันในทรานแซกชันเดียวกัน เพื่อไม่ให้เกิดกรณีที่สิทธิ์โปรโมชันหมดเร็วกว่าที่ควรจากคำสั่งซื้อที่ไม่เคยสำเร็จจริง

### เหตุใดจึงไม่มีสถานะ `returning` แยกจาก `refunding`

ทีมเคยพิจารณาว่าจะแยกสถานะ "อยู่ระหว่างการส่งสินค้าคืน" (`returning`) ออกจาก "อยู่ระหว่างดำเนินการคืนเงิน" (`refunding`) เพื่อความละเอียดที่มากขึ้น แต่ตัดสินใจไม่ทำเพราะพบว่าข้อมูลการส่งคืนสินค้าจริงๆ แล้วควรอยู่ในความรับผิดชอบของระบบโลจิสติกส์แยกต่างหาก ไม่ใช่ field ในตัว order state machine เอง — order state machine ควรตอบแค่คำถามระดับธุรกิจว่า "ตอนนี้ order นี้อยู่ในขั้นตอนไหนของความสัมพันธ์กับลูกค้า" ส่วนรายละเอียดการขนส่งกลับเป็นเรื่องของระบบปฏิบัติการที่แยกต่างหาก การแยกความรับผิดชอบแบบนี้สอดคล้องกับหลักการ service boundary ที่อธิบายไว้ในเอกสารสถาปัตยกรรมโดยรวม

### กรณี order ที่ลูกค้าสองบัญชีพยายามอ้างสิทธิ์เป็นเจ้าของพร้อมกัน

เกิดขึ้นได้ในสถานการณ์ที่ลูกค้าใช้บัญชีเดิมเช็คเอาท์บนอุปกรณ์สองเครื่องพร้อมกันโดยไม่ตั้งใจ เช่นเปิดแท็บเว็บไว้บนคอมพิวเตอร์แล้วลืมปิด จากนั้นสั่งซื้อซ้ำอีกครั้งบนมือถือ ระบบไม่ได้ป้องกันการสร้าง order ซ้ำสองใบในกรณีนี้เพราะแต่ละคำขอถือเป็น order ใหม่ที่ถูกต้องตามสิทธิ์ของบัญชีเดียวกันทั้งคู่ ทีมตัดสินใจไม่ implement การตรวจจับ duplicate order อัตโนมัติเพราะความเสี่ยงที่จะ false positive กับลูกค้าที่ตั้งใจสั่งซื้อสินค้าเดิมสองชิ้นจริงๆ สูงกว่าประโยชน์ที่ได้ ปล่อยให้เป็นหน้าที่ของลูกค้าเองที่จะสังเกตและติดต่อ support หากสั่งซ้ำโดยไม่ตั้งใจ ซึ่งกรณีแบบนี้จะถูกจัดการเป็นคำขอยกเลิกรายการปกติ

### ผลกระทบของ time zone ต่อการตีความ transition timestamp

ทุก timestamp ในระบบเก็บเป็น UTC เสมอที่ระดับ database แต่ทีม support ที่ดูแลลูกค้าในประเทศไทยมักอ้างอิงเวลาท้องถิ่นเมื่อพูดคุยกับลูกค้า ทำให้บางครั้งเกิดความสับสนว่า order เปลี่ยนสถานะ "เมื่อวาน" หรือ "วันนี้" กันแน่เมื่อเหตุการณ์เกิดใกล้เที่ยงคืน เพื่อลดความสับสนนี้ หน้า dashboard ภายในที่ทีม support ใช้จะแสดงเวลาทั้งสองรูปแบบคู่กันเสมอ (UTC และเวลาไทย) แต่ log ดิบที่วิศวกร debug ยังคงเก็บและแสดงเป็น UTC เท่านั้นตามมาตรฐานของระบบ log โดยรวม

### สรุปท้ายเอกสาร

เอกสารฉบับนี้ควรถูกอ่านควบคู่ไปกับ [[structure/module-order]] ที่อธิบายฝั่ง implementation และ [[business-logic/long-form-payment-lifecycle]] ที่อธิบาย state machine ของฝั่งการชำระเงินซึ่งเป็นระบบพี่น้องที่ทำงานคู่ขนานกันตลอดเวลา ความเข้าใจทั้งสองเอกสารพร้อมกันคือกุญแจสำคัญที่ทำให้ debug ปัญหาที่เกี่ยวข้องกับทั้งสอง state machine พร้อมกันได้อย่างมั่นใจ แทนที่จะเดาสุ่มว่าปัญหาอยู่ฝั่งไหน
