# Incident Response Runbook

เอกสารนี้เป็น runbook ฉบับเต็มสำหรับคนที่อยู่เวร on-call เขียนละเอียดเป็นพิเศษเพราะมักถูกอ่านตอนกลางดึกภายใต้ความกดดัน อยากให้ทุกขั้นตอนชัดจนไม่ต้องตีความ

## ปรัชญาของเอกสารนี้

on-call ไม่จำเป็นต้องเข้าใจ root cause ก่อนลงมือ หน้าที่อันดับหนึ่งคือทำให้ user ได้รับผลกระทบน้อยที่สุดก่อน ส่วนการหา root cause ค่อยทำทีหลังตอนใจเย็นลง ระบบ PayFlow เคยมีเหตุการณ์ที่ on-call พยายามหาสาเหตุให้เจอก่อนแล้วค่อย mitigate นานถึง 40 นาที ทั้งที่กด rollback ตั้งแต่นาทีที่ 5 ก็จบเรื่องได้แล้ว จากนั้นทีมจึงเขียนกติกาข้อนี้ไว้บนสุดของเอกสาร

## ระดับความรุนแรง (Severity)

### SEV1 — ระบบหลักใช้งานไม่ได้
ตัวอย่าง: ไม่มีใครสั่งซื้อได้เลย, payment gateway หลักล่มและ fallback ก็ไม่ทำงาน, database ของ order-service unreachable

ต้อง page คนทั้งทีมทันที ไม่ใช่แค่ on-call หลัก และต้องเปิด incident channel เฉพาะกิจใน 5 นาทีแรก

### SEV2 — ฟีเจอร์สำคัญพังบางส่วน
ตัวอย่าง: refund ค้างเป็นจำนวนมาก (ดู [[business-logic/refund-timeout-policy]] สำหรับนิยาม "ค้าง"), การแจ้งเตือนลูกค้าไม่ส่ง, checkout ช้าผิดปกติแต่ยังใช้งานได้

on-call หลักจัดการเองได้ อาจดึงคนที่สองมาช่วยถ้าจำเป็น

### SEV3 — กระทบน้อย ไม่เร่งด่วน
ตัวอย่าง: หน้า admin dashboard ช้า, log บางส่วนหาย, alert false positive

จัดการในเวลาทำงานปกติได้ ไม่ต้องปลุกใครกลางดึก

## ขั้นตอนตอบสนองมาตรฐาน (ทุก severity)

### ขั้นที่ 1 — Acknowledge (เป้าหมาย: ภายใน 2 นาที)

กด acknowledge ใน PagerDuty ทันทีที่ได้รับ alert แม้จะยังไม่รู้ว่าเกิดอะไรขึ้น การ acknowledge บอกทีมว่า "มีคนกำลังดูอยู่แล้ว" ป้องกันไม่ให้หลายคนพยายามแก้เรื่องเดียวกันพร้อมกันโดยไม่ประสานงาน

### ขั้นที่ 2 — Assess (เป้าหมาย: ภายใน 5 นาที)

เปิด dashboard หลัก 3 ตัวพร้อมกัน:
- Error rate รวมของทุก service
- Payment success rate
- Queue depth ของ RabbitMQ

ตอบคำถามให้ได้ก่อนลงมือแก้อะไร: กระทบ user กี่ % และเป็น severity ระดับไหนตามเกณฑ์ข้างบน ถ้าตอบไม่ได้ภายใน 5 นาทีให้ประกาศเป็น SEV2 ไว้ก่อนแล้วค่อยปรับลดทีหลัง ปลอดภัยกว่าการประเมินต่ำเกินจริง

### ขั้นที่ 3 — Mitigate (เป้าหมาย: ก่อนหา root cause)

ลำดับการพิจารณา mitigation ที่ทีมใช้ประจำ เรียงจากง่าย/เร็วที่สุดไปยาก:

1. **Rollback ได้ไหม** — ถ้า incident เริ่มหลัง deploy ล่าสุดไม่นาน ให้สงสัย deploy นั้นก่อนเสมอ ทำตาม [[deployment/rollback-procedure]] ทันที อย่ารอ
2. **Scale เพิ่มได้ไหม** — ถ้าเป็นเรื่อง load สูงเกิน capacity การเพิ่ม replica ชั่วคราวอาจซื้อเวลาได้
3. **ปิดฟีเจอร์ที่มีปัญหาได้ไหม** — ระบบมี feature flag สำหรับปิด non-critical feature (เช่น promo code, loyalty points) โดยไม่กระทบ core flow การสั่งซื้อ/ชำระเงิน
4. **Failover ไป fallback ได้ไหม** — เช่น payment gateway หลักล่ม ให้สลับไป 2C2P ผ่าน config โดยไม่ต้อง deploy ใหม่

**ห้ามลงมือแก้โค้ดสดบน production ระหว่าง incident** ไม่ว่าจะมั่นใจแค่ไหน — การแก้แบบเร่งด่วนมักสร้างปัญหาที่สองซ้อนทับปัญหาแรก ถ้าไม่มี mitigation สำเร็จรูปให้ rollback เป็นค่าเริ่มต้นเสมอ

### ขั้นที่ 4 — Communicate (ต่อเนื่องตลอด incident)

โพสต์ update ใน incident channel ทุก 15 นาทีแม้จะไม่มีความคืบหน้าใหม่ — ความเงียบทำให้คนอื่นเข้าใจผิดว่าไม่มีใครดูอยู่ ข้อความอัปเดตควรมี 3 ส่วนเสมอ: สถานะปัจจุบันเป็นยังไง, กำลังลองอะไรอยู่, คาดว่าจะรู้ผลเมื่อไหร่

ถ้า SEV1 ที่กระทบลูกค้าเห็นได้ชัด (เช่น สั่งซื้อไม่ได้ทั้งระบบ) ต้องแจ้งทีม customer support ให้เตรียมคำตอบมาตรฐานสำหรับลูกค้าที่ทักเข้ามาด้วย

### ขั้นที่ 5 — Resolve

ปิด incident เมื่อ metric กลับสู่ปกติต่อเนื่อง 15 นาที ไม่ใช่ทันทีที่ตัวเลขดูดีขึ้นครั้งแรก เพราะบาง mitigation (เช่น scale เพิ่ม) แก้ปัญหาที่ปลายเหตุ ถ้าต้นเหตุยังไม่หายตัวเลขอาจแกว่งกลับมาแย่อีกได้

### ขั้นที่ 6 — Postmortem (ภายใน 3 วันทำการ)

เขียน postmortem แบบ blameless เสมอ — เป้าหมายคือหาช่องโหว่ของระบบ ไม่ใช่หาคนผิด หัวข้อที่ต้องมี: timeline เหตุการณ์, impact ต่อ user, root cause, action item พร้อมเจ้าของงานและ deadline

## เคสตัวอย่างที่เคยเกิดจริงและใช้เป็นแนวทาง

### กรณี payment gateway timeout ต่อเนื่อง (กุมภาพันธ์ 2026)

payment gateway หลักเริ่มตอบช้าผิดปกติ ทำให้ `chargePayment` (ดู [[structure/module-payment]]) timeout เป็นจำนวนมาก ทีม on-call สลับไปใช้ 2C2P เป็น fallback ภายใน 8 นาทีตามขั้นตอน mitigation ข้อ 4 ทำให้ payment success rate กลับมาปกติก่อนที่จะรู้ด้วยซ้ำว่า gateway หลักมีปัญหาอะไร ภายหลังพบว่าเป็นปัญหาฝั่ง gateway provider เอง ไม่ใช่ปัญหาที่ระบบ PayFlow แก้ไขได้โดยตรง แต่การมี fallback พร้อมสลับได้ทันทีคือสิ่งที่ทำให้ user แทบไม่รู้สึกถึงผลกระทบ

### กรณี refund ค้างจำนวนมากพร้อมกัน (เมษายน 2026)

refund-service เริ่ม mark คำขอเป็น `stuck` จำนวนมากพร้อมกันในช่วงเวลาสั้นๆ ตรวจสอบพบว่าเกิดจาก payment gateway (คนละตัวกับกรณีข้างบน) ตอบ webhook ยืนยันการคืนเงินช้ากว่าปกติมาก ทีมตัดสินใจไม่ rollback เพราะไม่ใช่ปัญหาจาก deploy แต่เพิ่ม `REFUND_STUCK_THRESHOLD_MIN` ชั่วคราวจาก 15 เป็น 30 นาทีเพื่อลด false positive ของสถานะ stuck ระหว่างที่ gateway กำลังฟื้นตัว แล้วค่อยปรับกลับหลังสถานการณ์คลี่คลาย เคสนี้เป็นตัวอย่างที่ดีว่า mitigation ไม่จำเป็นต้องเป็น rollback หรือ scale เสมอไป บางครั้งการปรับ threshold ชั่วคราวก็เพียงพอ

## สิ่งที่ไม่ควรทำระหว่าง incident

- อย่าพยายาม fix root cause แบบสมบูรณ์แบบระหว่างที่ user ยังได้รับผลกระทบอยู่ — mitigate ก่อนเสมอ
- อย่า deploy hotfix ที่ไม่ผ่าน CI pipeline เต็มรูปแบบ แม้จะดูเป็นการแก้เล็กน้อยแค่ไหน ดู [[deployment/monitoring-alerts]] เพื่อยืนยันว่า alert หายจริงก่อนประกาศ resolve
- อย่าตัดสินใจคนเดียวสำหรับ SEV1 — ต้องมีคนที่สองรับรู้และเห็นด้วยกับ mitigation ที่เลือก แม้จะเป็นเวลากลางดึกก็ตาม

## ภาคผนวก: บทบาทของแต่ละคนระหว่าง incident

การมี incident channel เปิดขึ้นมาไม่ได้แปลว่าทุกคนที่เข้ามาจะทำงานแบบเดียวกัน ทีมพบว่า incident ที่จัดการได้ดีที่สุดมักมีการแบ่งบทบาทชัดเจนตั้งแต่ต้น แม้จะไม่มีเวลาประชุมกำหนดบทบาทอย่างเป็นทางการก็ตาม

### Incident Commander

คนแรกที่ acknowledge alert โดยปริยายจะรับบทบาทนี้ไปก่อน จนกว่าจะมีคนอื่นรับช่วงต่ออย่างชัดเจน หน้าที่หลักคือตัดสินใจเรื่อง mitigation ไม่ใช่ลงมือแก้โค้ดเอง Incident Commander ควรเป็นคนที่มองภาพรวมได้ ไม่ใช่คนที่จมอยู่กับรายละเอียดทางเทคนิคจุดใดจุดหนึ่งมากเกินไป ถ้า Incident Commander พบว่าตัวเองกำลังก้มหน้าก้มตาแก้โค้ดอยู่นานเกิน 5 นาที นั่นเป็นสัญญาณว่าควรส่งมอบบทบาทให้คนอื่นดูภาพรวมแทน

### Communicator

รับผิดชอบโพสต์ update ทุก 15 นาทีตามที่กำหนดไว้ในขั้นตอนที่ 4 และเป็นจุดติดต่อกับทีมอื่นที่ไม่ได้อยู่ใน incident channel โดยตรง เช่นทีม customer support หรือทีมผู้บริหารที่อาจต้องการทราบสถานะ บทบาทนี้สำคัญมากสำหรับ SEV1 เพราะ Incident Commander และวิศวกรที่กำลังแก้ปัญหาไม่ควรถูกขัดจังหวะด้วยคำถามสถานะซ้ำๆ จากคนนอก incident channel

### Responder

วิศวกรที่ลงมือแก้ปัญหาจริง อาจมีหลายคนพร้อมกันถ้าปัญหาซับซ้อนและต้องดูหลาย service พร้อมกัน แต่ทีมมีกติกาว่าไม่ควรมี Responder เกิน 3 คนทำงานพร้อมกันในปัญหาเดียว เพราะการประสานงานระหว่างคนมากเกินไปมักทำให้ช้าลงมากกว่าเร็วขึ้น ถ้าต้องการคนเพิ่มมากกว่านั้นมักแปลว่าควรแบ่งปัญหาออกเป็นหลายส่วนที่ทำคู่ขนานกันได้แทน

## ภาคผนวก: เกณฑ์การเลือก mitigation เมื่อมีหลายทางเลือกพร้อมกัน

บางครั้ง incident หนึ่งครั้งมี mitigation ที่เป็นไปได้มากกว่าหนึ่งทาง เช่น ทั้ง rollback และ failover ไป fallback gateway ต่างก็ดูเหมือนจะแก้ปัญหาได้ ในสถานการณ์แบบนี้ทีมใช้เกณฑ์เรียงลำดับความสำคัญดังนี้เสมอ

ความเร็วในการ mitigate สำคัญกว่าความสมบูรณ์ของการแก้ปัญหา — เลือกทางที่ทำให้ user กลับมาใช้งานได้เร็วที่สุดก่อน แม้จะไม่ใช่การแก้ปัญหาที่ต้นเหตุจริงๆ ก็ตาม ทางที่เคยทดสอบมาก่อนแล้วสำคัญกว่าทางที่ไม่เคยลองมาก่อน — เช่น failover ไป fallback gateway ที่เคยทดสอบใน game day มาก่อนน่าเชื่อถือกว่าทางแก้ใหม่ที่ยังไม่เคยพิสูจน์ ทางที่ reversible ได้ง่ายสำคัญกว่าทางที่ทำแล้วย้อนกลับยาก — ถ้าไม่แน่ใจว่า mitigation จะได้ผล ให้เลือกทางที่ถ้าผิดพลาดแล้วยกเลิกได้เร็ว มากกว่าทางที่ทำแล้วแก้คืนยาก แม้ทางหลังจะดูมีโอกาสสำเร็จสูงกว่าเล็กน้อยก็ตาม

## ภาคผนวก: การเตรียมความพร้อมก่อนเกิด incident (Game Day)

ทีมจัดกิจกรรม "game day" ทุกไตรมาสเพื่อจำลองสถานการณ์ incident แบบควบคุมได้ในสภาพแวดล้อม staging เป้าหมายหลักไม่ใช่การทดสอบว่าระบบทนทานแค่ไหน แต่เป็นการทดสอบว่ากระบวนการตอบสนองของ "คน" ราบรื่นแค่ไหนเมื่อเกิดเหตุจริง

สถานการณ์จำลองที่ใช้บ่อยที่สุดคือการตัด network connection ระหว่าง payment-service กับ payment gateway หลักโดยตั้งใจ เพื่อดูว่าทีมที่ไม่รู้ล่วงหน้าว่าจะเกิดอะไรขึ้นจะตรวจจับและ mitigate ได้เร็วแค่ไหนตามขั้นตอนที่เขียนไว้ในเอกสารนี้ ผลลัพธ์จาก game day ที่ผ่านมาพบว่าจุดที่ทีมมักทำได้ช้าที่สุดไม่ใช่ขั้นตอน mitigate แต่เป็นขั้นตอน assess — การตัดสินใจว่าเป็น SEV ระดับไหนมักใช้เวลานานกว่าที่ควรเพราะทีมพยายามหาสาเหตุให้แน่ชัดก่อนตัดสินใจ ทั้งที่เอกสารนี้ระบุชัดเจนแล้วว่าไม่จำเป็นต้องรู้สาเหตุก่อนจะประกาศ severity

หลังจาก game day ทุกครั้งทีมจะปรับปรุงเอกสาร runbook นี้ตามช่องว่างที่พบ เอกสารฉบับปัจจุบันจึงเป็นผลจากการปรับปรุงหลายรอบ ไม่ใช่ทฤษฎีที่เขียนขึ้นลอยๆ โดยไม่เคยผ่านการทดสอบจริง แนวทางนี้ยึดหลักเดียวกับปรัชญาของ postmortem แบบ blameless — เอกสารกระบวนการที่ดีต้องพัฒนาไปเรื่อยๆ ตามความเป็นจริงที่เจอ ไม่ใช่เขียนครั้งเดียวจบแล้วไม่มีใครแตะอีก

## ภาคผนวก: เครื่องมือที่ใช้บ่อยระหว่าง incident

รายการเครื่องมือและ dashboard ที่ on-call ควรเปิดค้างไว้ในแท็บพร้อมใช้งานตลอดเวลาที่อยู่เวร ไม่ใช่ค่อยไปเปิดหาตอนเกิดเหตุจริงซึ่งจะเสียเวลาโดยไม่จำเป็น: dashboard error rate รวม, dashboard payment success rate, PagerDuty mobile app ที่เปิด notification ไว้เสมอ, Slack channel `#incident` และ `#alerts` ปักหมุดไว้ด้านบน, และ CLI tool สำหรับสั่ง rollback ที่ login ค้างไว้ล่วงหน้าเพื่อไม่ต้องเสียเวลา authenticate ใหม่ตอนกดดัน

รายการนี้ควรถูกตรวจสอบว่ายังใช้งานได้จริงทุกครั้งที่เริ่มเวร on-call ใหม่ ไม่ใช่แค่ตอนเข้าทีมครั้งแรกครั้งเดียว เพราะ credential หมดอายุหรือ tool เปลี่ยน URL เป็นเรื่องที่เกิดขึ้นได้เงียบๆ โดยไม่มีใครแจ้ง จนกว่าจะพบว่าใช้งานไม่ได้ตอนเกิดเหตุจริงซึ่งเป็นเวลาที่แย่ที่สุดที่จะมาพบปัญหานี้

เอกสารนี้ควรอ่านคู่กับ [[deployment/rollback-procedure]] สำหรับรายละเอียดขั้นตอน rollback แบบเจาะจง และ [[deployment/monitoring-alerts]] สำหรับความหมายของ alert แต่ละตัวที่อาจเป็นจุดเริ่มต้นของ incident หนึ่งครั้ง การรู้จักเอกสารทั้งสามฉบับนี้พร้อมกันคือพื้นฐานขั้นต่ำที่ทีมคาดหวังจากทุกคนที่เข้าเวร on-call ครั้งแรก
