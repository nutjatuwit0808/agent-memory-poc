# Workshop 05 — Frontend comparison UI

## คำถามตั้งต้น

- ความต่างที่ `bench` วัดได้ **มองเห็นด้วยตาตอนพิมพ์ query เองได้ไหม** — หรือเห็นแค่ในตัวเลขเฉลี่ย
- ผลลัพธ์ที่ backend หนึ่งเจอแต่อีกตัวไม่เจอ คือไฟล์ไหนบ้าง (ตัวเลข recall เฉลี่ยซ่อนเรื่องนี้ไว้)
- latency ที่ user **รู้สึกจริง** ต่างจาก engine latency แค่ไหน — HTTP + render กลบอะไรไปบ้าง

## ทฤษฎีสั้น

`bench` วัดค่าเฉลี่ยจาก query set ตายตัว 20 ข้อ → เห็นภาพรวมแต่ไม่เห็นเคสเฉพาะที่ผู้เรียนสงสัยเอง UI แบบ side-by-side ทำให้เห็นสิ่งที่ค่าเฉลี่ยซ่อนไว้: **ผลลัพธ์ที่ต่างกันจริงต่อ query เดียว**

กับดักที่ต้องระวังที่สุดคือ**การจับเวลาผิดที่** — ถ้าวัดฝั่ง browser จะได้ HTTP + JSON + render รวมมาด้วย ซึ่งใหญ่กว่า engine time ของ fts5 หลายสิบเท่า จนตัวเลขที่โชว์กลายเป็นการวัด "ความเร็วเน็ต" ไม่ใช่ "ความเร็ว backend" (ดูตัวเลขจริงในหัวข้อผลการวัด — ถ้าดูแต่ round-trip จะประเมินความต่างต่ำกว่าความจริงถึง **27 เท่า**)

## วิธีรัน

ต้องรัน **2 process** (ผลจาก D-7 ที่เลือกสถาปัตยกรรมแบบแยก process):

```bash
# terminal 1 — search engine (ต้องมี rg ใน PATH)
npm run serve          # http://localhost:4000

# terminal 2 — UI
cd web && npm run dev  # http://localhost:3000
```

## Implementation

### D-7 — ทำไมต้องแยก process (ไม่ใช่ import ตรงใน API route)

ตรวจโค้ดก่อนเริ่มพบว่ามี **6 ไฟล์ใน `src/` ที่ผูก path กับ `import.meta.url`**
(`embedder.ts`, `embedding-cache.ts`, `reindex-core.ts`, `sqlite-db.ts`, `backends/index.ts`, `bench.ts`)

ถ้าให้ Next bundle โค้ดเหล่านี้เข้า `.next/server/` แล้ว `__dirname` จะย้ายที่ → หา `vault/`, `data/index.sqlite`, `data/models/` **ไม่เจอทั้งหมด** ทางแก้คือต้องรื้อ path resolution ทั้ง 6 ไฟล์เพื่อรองรับ UI ซึ่งขัดหลัก CLAUDE.md §2.4 โดยตรง

การแยกเป็น HTTP server (`src/cli/serve.ts` ด้วย `node:http` — **0 dependency**) ทำให้:
- โค้ดเดิมใน `src/` ไม่ถูกแตะเลยแม้แต่บรรทัดเดียว
- ไม่ต้องตั้ง `serverExternalPackages` ให้ native module (`better-sqlite3`, `onnxruntime-node`, `@lancedb/lancedb`)
- `web/next.config.mjs` แทบว่างเปล่า — ไม่มี config พิเศษสักตัว

### เส้นแบ่งที่บังคับไว้: `web/` ห้ามมี logic การค้นหา

**ทุกการคำนวณอยู่ฝั่ง server ทั้งหมด** — ไม่ใช่แค่ search แต่รวมถึง metric ด้วย:

| สิ่งที่ต้องแสดง | คำนวณที่ไหน | ทำไม |
|---|---|---|
| ผลค้นหา + score | backend เดิม (WS01–04) | UI เป็นแค่หน้าต่างมอง |
| `recall@5` / `precision@5` / MRR | `serve.ts` ด้วยสูตรเดียวกับ `bench.ts` | ถ้าสูตรสองฝั่งเพี้ยนกันแม้นิดเดียว ตัวเลขที่ UI โชว์จะไม่ตรงกับ README แล้วผู้เรียนจะไม่รู้ว่าควรเชื่อตัวไหน |
| ที่มาคะแนน RRF | `router.getLastFusion()` (เพิ่มใหม่) | ถ้า UI คำนวณ `1/(60+rank)` เองจะกลายเป็นเลขคนละชุดกับที่ router ใช้จริง |

สิ่งเดียวที่ `web/` คำนวณเองคือ **การนับว่า note ถูกคืนโดยกี่ backend** เพื่อระบายสีผลที่ไม่ซ้ำใคร — เป็นการนับเพื่อแสดงผลล้วนๆ ไม่แตะการจัดอันดับหรือคะแนนของใครเลย

### สิ่งที่เพิ่มเข้า `src/` (2 อย่าง ทั้งคู่เป็น additive)

1. **`src/cli/serve.ts`** — ไฟล์ใหม่ ไม่แตะของเดิม
2. **`router.ts`: `fuseRRFWithBreakdown()` + `getLastFusion()`** — `fuseRRF()` เดิมกลายเป็น wrapper บางๆ ของตัวใหม่ **signature ไม่เปลี่ยน** และ unit test เดิม 11 ตัวยังผ่านครบ

### ยิงแยก request ต่อ backend — ความไม่พร้อมกันคือบทเรียน

browser ยิง 5 requests ขนานกัน แต่ละคอลัมน์ render ทันทีที่ตัวเองเสร็จ ทำให้**เห็นกับตาว่า fts5 เสร็จก่อน ripgrep** ถ้ายิงรวมเป็น request เดียวทุกคอลัมน์จะรอตัวช้าสุดพร้อมกันหมด แล้วความต่างจะหายไปจากหน้าจอทันที

มี debounce 350ms + `AbortController` ยกเลิก request ชุดเก่า เพราะ ripgrep spawn subprocess ทุกครั้ง — ถ้าปล่อยให้พิมพ์เร็วๆ แล้ว request กองกันจะกิน CPU ฟรี

### Warm-up ตอน startup — เรื่องความถูกต้อง ไม่ใช่ optimization

log จริงตอนเปิดเซิร์ฟเวอร์ครั้งแรก:

```
warm  ripgrep       38.4ms
warm  fts5          0.6ms
warm  vector      1628.4ms   <-- ONNX compile execution graph สำหรับ shape ใหม่ (batch=1)
warm  router-fuse   31.1ms
```

ตรงกับที่ W3-1 เจอไว้ (~1,250ms) ถ้าไม่ warm ผู้ใช้คนแรกจะเห็น vector ช้ากว่าความจริงเกือบ 2,000 เท่าแล้วสรุปผิดทันที รอบถัดมาเหลือ 0.8ms

## ผลการวัด

### 1. engine time vs round-trip — ทำไมต้องแยกให้เห็น

จาก preset `q-semantic-card-rejected` (วัดจริงบนหน้าเว็บ):

| backend | engine (server) | round-trip (browser) |
|---|---|---|
| ripgrep | 43.51ms | 49.8ms |
| fts5 | 0.50ms | 15.6ms |

- ดูที่ **engine**: ripgrep ช้ากว่า fts5 **87 เท่า**
- ดูที่ **round-trip**: ripgrep ช้ากว่า fts5 แค่ **3.2 เท่า**

**ถ้า UI โชว์แต่ round-trip จะประเมินความต่างต่ำกว่าความจริง 27 เท่า** — เพราะ overhead คงที่ ~15ms ของ HTTP+JSON กลบ engine time ของ fts5 (0.50ms) จนแทบมองไม่เห็น นี่คือเหตุผลที่ต้องวัดฝั่ง server แล้วส่งตัวเลขกลับมา

### 2. สลับกันแพ้ชนะภายในสองคลิก (ผลจาก UI จริง)

**คลิกที่ 1 — preset `exact`: `PAYMENT_GATEWAY_TIMEOUT_MS`**

| backend | recall@5 | ✓ hits | ผลที่ไม่มีใครเจอ |
|---|---|---|---|
| ripgrep | **1.00** | 3 | 0 |
| fts5 | **1.00** | 3 | 0 |
| vector | **0.00** | 0 | **3** |
| router-route | **1.00** | 3 | 0 |
| router-fuse | **1.00** | 3 | 0 |

vector หาไม่เจอเลยสักไฟล์ แถมยังไปเจอ 3 ไฟล์ที่ไม่มี backend อื่นเจอ (คือเดาผิดอยู่คนเดียว) — เห็นชัดว่า embedding มอง identifier เป็นแค่ "คำแปลกๆ" ที่ไม่มีความหมายทางภาษา

**คลิกที่ 2 — preset `semantic`: `จ่ายเงินด้วยบัตรแล้วไม่ผ่านซ้ำๆ ควรทำยังไง`**

| backend | recall@5 | ผลลัพธ์ที่คืนมา |
|---|---|---|
| ripgrep | **0.00** | **ไม่พบผลลัพธ์เลย** (เสียเวลา 43ms ฟรี) |
| fts5 | **0.00** | **ไม่พบผลลัพธ์เลย** |
| vector | **1.00** | เจอ `case-3210.md` เป็นอันดับ 1 (score 0.4802) |
| router-route | **1.00** | เลือกกฎ `long-semantic` → vector ถูกต้อง |

ภาพกลับด้านสมบูรณ์ ตรงกับตัวเลขใน WS01–03 ทุกประการ

### 3. Layer pre-filter (วัดผ่าน `?repeat=20` วิธีเดียวกับ `bench.ts`)

| backend | ไม่มี filter | มี `layer=business-logic` | Δ |
|---|---|---|---|
| ripgrep | 30.43ms | 31.07ms | **+2%** (ไม่ได้ประโยชน์ — post-filter) |

| vector | 0.134ms | 0.086ms | **−36%** |

ยืนยันข้อสรุปของ W4-2 ซ้ำอีกครั้งด้วยเส้นทางคนละแบบ: ripgrep กรองทีหลังจึงไม่ประหยัดงานเลย ส่วน fts5/vector กรองก่อนคำนวณจึงลดงานได้จริง

## สรุปสิ่งที่พบ

**UI ทำให้เห็นสิ่งที่ตาราง bench บอกไม่ได้ 3 อย่าง:**

1. **"ไม่พบผลลัพธ์เลย" ต่างจาก "recall ต่ำ" มาก** — ตาราง bench บอกว่า ripgrep มี semantic recall 0.07 ซึ่งฟังดูเหมือน "แม่นน้อย" แต่บนหน้าจอจริงคือ **ช่องว่างเปล่า** หลังรอไป 43ms ความรู้สึกของผู้ใช้ต่างกันคนละเรื่องกับตัวเลข 0.07
2. **ผลที่ผิดคนเดียวมองเห็นได้ทันที** — แถบเหลือง (ผลที่ไม่มี backend อื่นเจอ) ทำให้เห็นว่าตอน vector แพ้ มันไม่ได้แค่ "หาไม่เจอ" แต่ไป**เจอของผิดมาแทน**อย่างมั่นใจ ซึ่ง recall เฉลี่ยไม่เคยบอกเรื่องนี้
3. **ต้นทุนคงที่กลบความต่างของ engine ได้ง่ายมาก** — ความเร็ว 87 เท่าของ fts5 เหลือแค่ 3.2 เท่าเมื่อมองผ่าน HTTP ซึ่งเป็นบทเรียนตรงๆ ว่าการ optimize ส่วนที่ไม่ใช่คอขวดไม่ช่วยอะไรเลยในระบบจริง

**ข้อควรระวังที่เจอระหว่างทำ:** `next dev` (v16) สร้าง `AGENTS.md` และ `CLAUDE.md` ลงใน `web/` อัตโนมัติ ซึ่งชนกับคอนเวนชันของโปรเจกต์ที่ `CLAUDE.md` ที่ root คือสัญญาการออกแบบตัวจริง — ปิดด้วย `agentRules: false` ใน `next.config.mjs`

**ข้อจำกัดที่ยังไม่ได้แก้:** ตัวเลข engine time ที่ UI โชว์เป็นการวัดครั้งเดียว (single-shot) ซึ่งแกว่งกว่า p50 จาก `bench` พอสมควร โดยเฉพาะ ripgrep ที่ผูกกับ OS process spawn — API รองรับ `?repeat=20` ให้วัดแบบเดียวกับ bench แล้ว แต่ยังไม่มีปุ่มบน UI ให้กด
